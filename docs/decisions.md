## Intake & n8n boundary

| # | Question | Why it matters | Decision | Date |
|---|---|---|---|---|
| 3 ✅ | How does FastAPI authenticate a request as genuinely from n8n? | Unauthenticated intake endpoint = anyone who finds the URL can inject fake proposals. | **Static shared-secret header** (e.g. `X-Intake-Secret`) sent by the n8n HTTP Request node, checked by a FastAPI dependency on `POST /intake`. Store as an env var on both sides — never inline it in the n8n workflow JSON export. HTTPS-only transport; rotate if the workflow JSON is ever shared externally. | 2026-09-08 |
| 4 ✅ (revised) | Is the intake hop idempotent? | n8n *will* retry failed webhook deliveries; without an idempotency key you get duplicate proposals. | ~~`hash(timestamp + email_address)`~~ — superseded 2026-09-09: this only caught automated n8n retries, not a salesperson genuinely resubmitting the same form (same content, new `Timestamp`). **Revised to `hash(company_name + normalize(project_scope) + respondent_email)`** — covers both cases, since a real duplicate submission shares these three fields regardless of timestamp. `normalize()` = lowercase/trim/collapse-whitespace/strip-trailing-punctuation, computed by FastAPI. FastAPI enforces a DB unique constraint on this key on `IntakeSubmission`; `POST /intake` is an upsert (return existing `Proposal` id on conflict). See `docs/edge-cases.md`. | 2026-09-08 (revised 2026-09-09) |
| 5 🟠 | What's the canonical intake schema, and who keeps Form/Sheet/API in sync? | Three places the same shape must match; nothing today catches drift when a form question is edited. | **Mechanism decided:** an n8n Code node normalizes Google Sheets field names to canonical API keys before the HTTP call (see `docs/intake-schema.md`). FastAPI's Pydantic model remains the enforced contract, 422s on drift. **Drift handling implemented 2026-09-10** (see `docs/edge-cases.md` "n8n error branch + backend alert-logging built for schema drift"): the Code node passes unmapped columns through under their raw header rather than dropping them, so `extra="forbid"` catches a newly-added form field as a real 422; the Code node also validates required fields before the HTTP call; FastAPI's `/intake` route logs a greppable `INTAKE_SCHEMA_DRIFT`/`INTAKE_AUTH_FAILED` tag on every 422/401 (`backend/app/main.py`, `backend/app/api/v1/endpoints/intake.py`) so log-based monitoring can alert independent of n8n's own alert node. **Real gap, not yet resolved:** the Code node's own thrown validation error has no `onError` wired, so it fails the n8n execution before FastAPI (and the new backend logging) ever sees the request — needs a decision between wiring `continueErrorOutput` into n8n's `Alert` node vs. having the Code node forward rather than throw, so Pydantic's 422 is the single detection point. n8n's `Alert` node is also still a placeholder (no real channel wired). A question reworded without changing its key/column remains undetectable by any technical check — process-only fix (update `docs/intake-schema.md` → n8n mapping → confirm against Pydantic). **Still open:** the exact canonical field list isn't fully locked — `docs/intake-schema.md` is the working draft; confirm it before Phase 1 schema freeze. | 2026-09-08 (drift handling implemented 2026-09-10) |
| 6 ✅ | Is n8n the permanent intake mechanism? | Changes how much hardening the n8n step deserves. | **No — a bridge.** Flow is Form → Sheets → n8n → FastAPI for now. A future native intake form connects directly to FastAPI using the same canonical schema, bypassing n8n entirely. | 2026-09-08 |

| # | Question | Why it matters | Decision | Date |

| 7 ✅ | Final document format? | Determines the entire Phase 6 tooling choice. | **Branded PDF**, generated for email delivery. PDF rendering fidelity needs explicit test coverage (see `CLAUDE.md` Testing Requirements). | 2026-09-08 |
| 8 ✅ | Fixed template or variable per client/engagement? | Determines whether "sections" are a fixed enum or a dynamic list. | **Fixed** — the existing reference template's 6 sections, in order, for the initial version (Introduction, Proposed Solution, Deliverables, Timeline, Pricing, Next Steps — see `docs/intake-schema.md`). Configurable/per-client sections deferred, not required for v1. | 2026-09-08 |
| 9 ✅ | Is the approved document immutable? Does a post-approval change require full re-approval? | Affects whether `DocumentArtifact` is append-only or can be superseded quietly. | **Resolved 2026-09-11**: a post-approval edit/regeneration forces the Proposal back to `IN_REVIEW` and resets that section's approval status (`regeneration.py::regeneration_invalidates_approval`, Phase 3/4, unchanged). Once the proposal is re-approved (`APPROVED` reached a second time), `generate-document` is re-triggerable — `document_service.start_document_generation` now deletes the stale `DocumentArtifact` (an existing artifact at this point is always superseded content, never a duplicate of the same approval, since `transition_proposal` itself rules out reaching `APPROVED` twice without an intervening edit) and lets a fresh PDF get generated, reusing the same deterministic Storage path (`upload_pdf`'s upsert overwrites the old object, no orphaned file left behind). `DocumentAlreadyGeneratedError` removed as dead code — the only thing that can still block generation is `InvalidTransitionError` (wrong status). **Still open, surfaced by this same discussion:** `ProposalSection` has no version history — `content`/`version` are overwritten in place on every edit/regeneration, so a re-approved-and-regenerated document has no way to show what a prior *approved* version of a section actually said. If that ever matters for compliance/dispute purposes, it needs a real section-version-snapshot table, not just the incrementing `version` int that exists today. | 2026-09-08 (resolved 2026-09-11) |

| 13 ✅ | Cap on regenerations / cost budget? | Unbounded "regenerate" is a direct, uncapped cost/abuse surface. | **Hard cap of 3 regeneration attempts per section.** Every regeneration call — not just the first — **requires** a salesperson-provided instruction/context; this is now mandatory input, not optional (tightens #10). | 2026-09-08 |
| 13b ✅ | Does the regeneration endpoint preserve the salesperson's instruction trail across attempts? | Without it, the 3-attempt cap (#13) becomes frustrating: the salesperson re-types instructions from memory each attempt, repeats themselves, and can't tell whether the last regeneration actually addressed what they meant. | **Implemented (Phase 4, 2026-09-10):** `ProposalSection.regeneration_log` (JSON column, migration `8277db7b3a4f`) — an append-only list, one entry per attempt (`instruction`, `attempted_at`, `outcome`, `resulting_version` or `error`), including failed attempts. Surfaced in `RegenerateSectionButton` as attempt history. Append-only, no edit/delete (the log records what was actually sent to Claude, not editable notes). Also resolved as part of the same work: what `content_origin` becomes after an edit vs. a regeneration (`backend/app/domain/content_origin.py`) — regeneration always sets `ai_generated`; a manual edit sets `human_edited_after_generation` if the prior content was AI-touched, else `human_edited`. See `docs/edge-cases.md` "Regeneration loses the salesperson's instruction context across attempts". | 2026-09-09 |
| 23 ✅ | Should the system generate a proposal from intake that's too sparse to write a real one from (e.g. "Goals: Goals", "Scope: deliverables")? | Claude will happily produce grammatically clean, confident-sounding sections from near-empty input — the failure is invisible unless someone deliberately looks for it, and it directly undermines "tailored to the client" as the entire value proposition of this tool. | **Detect and flag, don't block.** `hasThinIntake()` (`web-app/lib/proposal-status.ts`) flags a proposal when 2+ of the four narrative intake fields (`client_needs_summary`, `project_scope`, `goals_and_objectives`, `recommended_services`) are under 4 words — a threshold a genuine discovery-call answer essentially never falls under. Generation itself is **not** blocked (a salesperson may legitimately want to see the draft anyway, or the thin field may genuinely not matter for this client) — instead the proposal detail page shows an "Intake looks thin" warning banner with a one-click **"Email client for more detail"** action (a pre-filled `mailto:` naming the specific thin fields), so the salesperson can close the gap before investing further review time, rather than discovering it only after a generic-reading proposal is already drafted (or worse, sent). Deliberately a frontend-only heuristic, computed from fields already on `ProposalDetailResponse` — no backend schema change, no new Claude call to "judge" the intake. | 2026-09-11 |

## Roles (new — resolved 2026-09-08, supersedes the salesperson/approver split assumed earlier)

| # | Question | Why it matters | Decision | Date |
|---|---|---|---|---|
| 21 ✅ | Who can use the system — is there a distinct "approver" role? | Determines the entire RBAC model, not just the approval flow. | **Salespeople only, single role.** Even when admin staff prepare a proposal, they operate under the `salesperson` role for authorization purposes — there is no separate `approver` role. Dashboard access requires authentication; every protected frontend and backend request is authorized against this one role. **Open follow-up:** any authenticated salesperson may act on any proposal today (no per-proposal ownership restriction) — the deliberate interim default, since no segregation was stated. Real login landed 2026-09-11 (see #22 below), but the ownership-based access model itself (a proposal already assigned to a salesperson editable only by them; an unassigned one self-claimable, decisions #20) is still not built — recorded as the future plan in `docs/reference/data-retention-policy.md`'s "Future" section, blocked on nothing now except doing the work. | 2026-09-08 |
| 22 ✅ | How do salespeople actually authenticate — and does a self-serve signup alone grant real access? | An open `signUp()` that instantly grants access to client PII is a real security decision, not an implementation detail. | **Supabase Auth (email/password), both sign-in and self-serve sign-up, client-side via `@supabase/supabase-js`** — the frontend never touches the DB directly; it gets a JWT from Supabase's own Auth API and sends it as a Bearer token to this backend, which verifies the signature locally against `SUPABASE_JWT_SECRET` (`app/core/security.py::verify_token`). **Deliberately not enough on its own**: a real `signUp()` account is instantly JWT-issuing, so a `salesperson_accounts` table gates it — every account is created `pending` on its first authenticated request and rejected with 403 until an already-approved salesperson approves it (no separate approver role needed, consistent with #21 — approving a colleague requires no more privilege than approving a proposal). Bootstrap problem (nobody can approve the first account through the API) solved with `scripts/approve_salesperson.py`, run once directly against the DB, never exposed as an endpoint. The dev token bypasses this table entirely — it never had a real Supabase user behind it. See `docs/edge-cases.md`, 2026-09-11, for the security/production-readiness review of this flow. | 2026-09-11 |

## Intake attribution (surfaced 2026-09-08 while cross-referencing the PRD — resolved 2026-09-09)

| # | Question | Why it matters | Decision | Date |
|---|---|---|---|---|
| 20 ✅ | Either sales/admin staff *or the client* can submit the form, and `salesperson_name` is free text — how does a submitted proposal get reliably assigned to the correct `User` account? | Ownership drives authorization. A fragile name-string match will misassign proposals. | **`salesperson_name` is optional, both in the intake schema and the DB column.** Never string-match it to a `User` — a blank/whitespace value (client filled the form directly, no salesperson on the call) is normalized to `NULL` = "unassigned" (see `docs/edge-cases.md`).
