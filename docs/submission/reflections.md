# Reflections

## Model choice, and why

The system uses **Claude Sonnet 5** for every generation and regeneration call. I didn't just take the default and move on — I went back and actually ran the numbers (see `submission/model-cost-analysis.md`) at a realistic volume (2,000 proposals/month): the cost spread across *every* available Claude model — from Haiku 4.5 up to Fable 5.1 — comes out to roughly **$120/month total**. That's the real finding: at this task's scale (short, single-turn, non-agentic section drafting, capped at 500 output tokens), model choice basically isn't a cost decision at all. It's a quality decision. So I kept Sonnet 5 deliberately — it's positioned as the best speed/intelligence balance, and neither Opus 5 nor Fable 5.1's actual strengths (complex agentic coding, long-horizon multi-step reasoning) apply to what this app calls Claude for. Paying 2.5-5x more for capability the task can't use would have been the wrong call, and paying less (Haiku) to save $13/month isn't worth the risk to output quality without first actually testing it side-by-side, which I flagged as a real next step rather than guessing.

## The biggest technical challenge

Not the AI integration — the state machine. Every transition (`DRAFT → GENERATING → IN_REVIEW ⇄ PENDING_APPROVAL → APPROVED → ...`) had to be enforced in the backend, not just hidden behind a disabled button, and every async step (Claude generation, PDF rendering, email delivery) needed its own `*_FAILED` substate so a failure never left the system looking like "nothing happened" when something actually broke mid-flight. The trickiest part specifically was making sure a **failed** regeneration attempt didn't burn one of the salesperson's 3 tries — that required splitting "the call was made" from "the call succeeded and should count against the cap," which isn't obvious until you actually trace through what a rate-limit error mid-regeneration does to a naive implementation.

## A trade-off I made, and the lesson from it

I built the activity-log audit trail (Phase 8) *before* the PII/retention policy existed. That was backwards, and it showed: the first version of the audit log logged `company_name` on creation and `client_email` on delivery — directly violating a policy I hadn't written yet. Once the retention/PII policy was actually defined (`docs/reference/data-retention-policy.md`), I had to go back and strip that PII out of already-shipped code and already-written tests. The lesson: for anything that's explicitly a compliance/audit feature, define the data policy *first*, even a rough one, before building the thing that logs against it — otherwise you build something that has to be re-audited against a policy that arrives late.

## Other trade-offs, named explicitly

- **`salesperson_name` is optional, not required.** This removes attribution-at-intake in exchange for letting a client self-serve into the pipeline without a discovery call happening first. The alternative (require it) would guarantee ownership but reintroduce the friction step this was meant to remove.
- **Any authenticated salesperson can approve any proposal — no ownership gate, no approver role.** This matches how the team actually works (one role, self-approval expected), but it means there's currently no restriction on who touches what. Once real per-salesperson login landed, I documented (not yet built) the intended future model: an assigned proposal is only editable by its owner, and an unassigned one can be self-claimed.
- **RLS is deliberately not fully cut over.** I built the groundwork (a lower-privileged role, forced RLS policies, the session-flag code) because doing it partially or against the wrong role would be worse than not doing it — a naive `ENABLE ROW LEVEL SECURITY` while still connected as the table-owning role changes nothing and would have given a false sense of security. Finishing the cutover (new `DATABASE_URL`, a real password, testing against staging first) is left as an explicit next step rather than rushed.

## Designing real login: shipping fast vs. shipping open

Adding real per-salesperson login looked like a one-line change — wire up `supabase.auth.signUp()` and call it done. I deliberately didn't stop there, because a working Supabase account is instantly JWT-issuing: the naive version would have meant anyone who found the deployed URL could create an account and immediately read every client's PII with zero review, which is a materially worse state than the dev-token-only version it replaced. So the real work wasn't the login form, it was the approval gate behind it (`salesperson_accounts`, pending until an existing salesperson approves the next one) — same "no separate approver role" pattern already used for proposals, so it didn't need new RBAC machinery, just a new gated resource. The trade-off I made explicitly: self-serve sign-up stays open (no invite link, no email-domain check) because there's only one role to escalate to and the pending queue itself is low-stakes — but I flagged that as a real, if minor, surface (someone could spam-create pending accounts) rather than pretending it away.

## Catching "confidently generic" output before a human has to

While reviewing a real generated proposal I noticed the intake behind it was almost entirely placeholder-shaped ("Goals: Goals", "Scope: deliverables") — yet the generated sections read as a completely normal, well-formed proposal. That's a failure mode specific to this kind of tool: the model isn't wrong, the *input* was hollow, and nothing about the output signals that back to the person reviewing it. I decided this needed a deliberate design response, not a code fix — blocking generation on "bad" input felt wrong (a short answer can be legitimate, and a salesperson might have context the form didn't capture), so instead I built a thin-intake detector that flags it as a warning with a direct action attached (email the client for more detail) rather than a silent block or, worse, nothing at all. The part I'd call a real decision rather than an obvious one: choosing to *warn and let the human act* over *refuse to generate* — the second option is easier to build and feels "safer," but it would have taken away exactly the case where the salesperson already has the missing context and just wants the draft anyway.

## A production bug I didn't anticipate: two valid ways to sign a JWT

I shipped real login assuming Supabase always signs its JWTs with a shared HS256 secret, because that's the setup the original scaffolding assumed and it's what most Supabase tutorials still show. It turned out this project's Supabase instance issues tokens with the newer asymmetric signing mode (ES256, verified via JWKS, no shared secret involved at all) — so every real login failed with a genuinely confusing error message ("the specified alg value is not allowed") that reads like an expired-token problem but is actually "you're checking the wrong kind of signature entirely." The fix (read the token's own header, branch on signing mode) is straightforward once diagnosed, but the diagnosis itself is the lesson: an auth integration that "works" against a dev token or a manually-crafted test JWT hasn't actually been tested against the real identity provider's actual current configuration, and those can silently diverge from what a tutorial or an older scaffold assumed.

## Self-critique — what I'd flag to a reviewer before they find it themselves

- The n8n webhook secret is still inline plaintext in the workflow export, not in a secret manager. I caught this in review and it's documented as the first go-live task, but it shipped that way and should have been caught before it was ever exported in that form.
- The retention-enforcement script is built and tested, but nothing calls it on a schedule yet — a policy with no enforcement mechanism wired up is still just a policy.
- The deployed backend is on a free tier that cold-starts (~15-20s) — fine for a demo I can narrate around, not fine for a real user's first impression.
- I only caught the cookie-name mismatch that silently broke real login (`getClientAuthToken`/`setClientAuthToken` disagreed on the cookie name) because a real login attempt actually failed in front of me. That's a class of bug — two functions in the same file quietly disagreeing on a shared constant — that a code review focused on "does this function work in isolation" would miss, and it's worth remembering that the get/set/clear trio for anything stateful needs to be checked together, not one at a time.
